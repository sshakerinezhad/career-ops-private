# Algorithms drills: what a strong answer covers

For the interviewer (LLM persona or a person). Open only after the drill.

**Drill 1, slow unreliable comparator.** Restate: top-10 selection with a noisy, expensive oracle; two costs, calls and rounds (wall-clock = rounds × 5 s because calls are independent and can run in parallel). Brute force: full pairwise, ~2 million calls. Better: tournament or heap selection, O(n log k) comparisons; the wall-clock lever is parallel rounds, so structure as a bracket with depth log n, each round issued in parallel. Noise: a single 10% comparator gives ~10% wrong edges; repeat comparisons only where they matter (near the top-10 boundary, majority of 3 or 5 gives ~2.8% or ~0.9% error); or fit a rating model (Bradley-Terry / Elo) and choose pairs actively where the posterior is uncertain; noisy sorting is O(n log n) comparisons with high-probability guarantees. Edge cases: ties, intransitive comparators, adversarial pairs. Constraint change (error depends on closeness): more repeats on close pairs only, fewer on distant ones; the rating model handles this naturally. Verify: simulate with a known ground truth and measure top-10 recall vs calls. 10x: n = 20,000 still O(n log k) calls; the round depth barely grows; the cost is dominated by boundary refinement.

**Drill 2, token micro-batch packing.** Restate: bin packing with capacity 128k, plus load balance across ranks, plus items over capacity. Brute force: exponential. Better: first-fit-decreasing (sort by length descending, place each in the first bin with room), O(n log n), at most 11/9 OPT + 1 bins; for balance across ranks, LPT assignment of bins to ranks; over-capacity trajectories get context parallelism or are split with attention masks (sequence packing with per-sequence masks so tokens from different sequences do not attend). Constraint change (prompt_mean, keep a prompt's 8 trajectories together): pack at the prompt level (sum of the 8 lengths) or accept splitting across micro-batches within one optimizer step, since the loss aggregation is per prompt and the gradient accumulates across micro-batches anyway; say which. Verify: padding fraction and per-rank token variance. 10x: still O(n log n); the real limit is the longest trajectory, which sets the minimum capacity.

**Drill 3, dynamic sampling.** Restate: choose M prompts per step whose 8 rollouts will have mixed outcomes, under a budget of B rollouts, with unknown drifting pass rates. Brute force: sample all, filter, waste. Better: keep a per-prompt estimate of pass rate p with uncertainty (Beta posterior from recent outcomes, decayed so drift is tracked), rank prompts by expected informativeness p(1−p) or by the probability that 8 samples are mixed, 1 − p^8 − (1−p)^8, keep them in a heap, pop M, sample, update. Exploration: reserve a fraction for prompts with wide posteriors so all-fail prompts get re-tested as the policy improves (curriculum). Expected waste: for p = 0.5 almost every group is mixed; for p = 0.05 only about a third are. Constraint change (40% all-fail, 50k prompts): do not spend the budget re-testing all-fail prompts every step; re-test a decaying sample; the heap makes each update O(log P). Verify: fraction of zero-advantage groups per step, and the rate at which formerly all-fail prompts become mixed. 10x: same structure; the cost is in the rollouts, not the bookkeeping.

**Drill 4, near-duplicate tasks.** Restate: near-duplicate detection over 1M texts, then clustering, then cross-split checks. Brute force: 5 × 10^11 pairs. Better: exact hash first (normalize whitespace, case, numbers), then shingling (word n-grams) + MinHash signatures + LSH banding so only candidate pairs are compared, expected O(n); or embeddings + HNSW for paraphrases; union-find to form clusters; tune the threshold on a hand-labelled sample and report precision and recall; check duplicates across train/test splits. Constraint change (duplicates in attached files): hash file contents and extracted text; for spreadsheets, hash the cell values with numbers normalized; treat a task as a tuple of prompt and file fingerprints. Verify: sample clusters by hand, measure false-positive rate. 10x: LSH scales linearly; the index fits in memory if signatures are small.

**Drill 5, rollout scheduling with stragglers and staleness.** Restate: a queueing system; maximize completed rollouts per training step subject to a staleness bound. Brute force: synchronous batches, wait for the slowest rollout every step (the median-vs-tail gap makes this terrible). Better: a work queue with in-flight weight updates and partial rollouts; put a timeout on everything (Mercor's own first rule); the concurrency ceiling is min(KV-cache capacity in tokens / average trajectory length, the staleness bound (S + 1) × B × samples-per-prompt); abort or deprioritize rollouts that will exceed staleness; Little's law to size concurrency (L = λW); shortest-remaining-work first if remaining work is predictable, otherwise FIFO with preemption for stale work. Constraint change (KV cap C per engine, update every step): concurrency = K × C at most; if that is below the staleness ceiling, KV cache binds, and the lever is shorter trajectories (the wrap-up nudge) or more engines. Verify: measure the staleness distribution of trained samples and the engine utilization. 10x: more engines; the staleness bound scales with batch size, so the ceiling moves with the trainer.

**Drill 6, streaming Pass@k with confidence.** Restate: online estimation over tasks with a fixed number of samples each, plus a sequential comparison. Brute force: recompute everything on every arrival. Better: per-task counters (c_i successes of n_i seen); Pass@1 = mean over tasks of c_i / n_i; Pass@k needs the unbiased estimator 1 − C(n−c, k)/C(n, k), valid only when n_i ≥ k, so report Pass@8 only for completed tasks and say so; task-level bootstrap on demand (O(T × R)); Welford for running variance; incremental update is O(1) per arrival. Comparison: pair by task, track the running mean difference and its interval. Constraint change (stop early, peeking): fixed-alpha repeated testing inflates false positives; use a sequential test (e-values or an alpha-spending boundary) or pre-register the check times. Verify: simulate arrivals from a known ground truth and measure the false stop rate. 10x: counters scale linearly; the bootstrap is the only heavy step and can be sampled.

**Scoring each drill (0 to 2 each):** restated and confirmed; asked for scale before designing; brute force stated with its cost; bottleneck named; two approaches, one chosen with a reason; complexity and edge cases; 10x answer; empirical verification named. 12 to 16: ready. Under 10: repeat the protocol on the same drill next day.

## Drills 7 to 10 (added 2026-09-18: matching, ranking, graphs, orchestration)

**Drill 7, project-to-contractor matching.** Restate: a many-to-many assignment with capacities on both sides (contractor hours per week and availability; project skill slots and budget), maximizing filled project-hours. Confirm whether a contractor may split a week across projects and whether budget is in dollars or hours. Ask N, M, and the horizon. Brute force: enumerate assignments, exponential. Better: a flow problem. Bipartite network, contractor to (project, skill slot), edges where skills match and availability overlaps the window; contractor capacity on the source edge, project budget on the sink edge; max flow maximizes filled hours, min-cost flow when rates differ and budget is in dollars; weekly capacity means a time-expanded graph, one contractor node per week. Hungarian O(n³) only covers one-to-one. Greedy by cheapest matching contractor is not optimal: a contractor who fits two projects gets spent on the one where a substitute existed. If both sides rank each other, Gale-Shapley with capacities gives stability but does not maximize hours; say which objective the business wants. Edge cases: a skill nobody has; report it, do not fail the solve. Constraint change (online, irrevocable): no augmenting paths; with one side known in advance, greedy online matching is 1/2-competitive and RANKING (a random fixed order over that side) is 1 − 1/e; with both sides arriving, batch into short windows, solve flow per batch, and hold back some scarce-skill capacity. Verify: replay a historical month, compare the online rule's filled hours with the offline optimum. 10x: keep edges sparse with a skill index; split by region or skill family when projects rarely cross them.

**Drill 8, deterministic comparator under a budget.** Restate: top-20 selection plus a top-100 ranking over 5,000 items; a comparator wrong on a fixed 15% of pairs; 40,000 calls at 5 s each. Repeating a pair adds nothing here (unlike Drill 1), so majority-of-m is useless; redundancy comes from many different opponents per item. Arithmetic: 8 calls per item, wall clock rounds × 5 s since calls run in parallel; a full sort, n log2 n, about 61,000, is over budget; heap selection O(n log k), about 22,000, fits, but one wrong edge eliminates the best with no repair. Better, two phases: half the budget on a sparse round-robin (each item versus a few random opponents), score by win fraction, shortlist a margin above 100; then a dense comparison graph on the shortlist, fit Bradley-Terry (MLE of one strength per item from pairwise wins), take the top 100 and top 20 by strength; a wrong edge is a soft penalty, not an elimination. Constraint change (intransitive triples): a tournament is transitive iff it has no directed 3-cycle; count 3-cycles among closed triples (complete case: C(n,3) − Σ_v C(out-degree(v), 2)), buying closing edges for sampled triples. Independent flips at rate p on a true order already make p(1 − p) of triples cyclic, about 13% at p = 0.15; report cycles that cluster on specific items or exceed that rate, and mark those ranks unstable. Verify: simulate a planted order with a fixed 15% wrong-pair set; measure top-20 recall and top-100 rank correlation. 10x: 50,000 items on the same budget is under one call per item: phase 1 sparser, shortlist noisier, rounds barely grow.

**Drill 9, referral network.** Restate: per-node reach count, expected bounty through each node, and expected total payout on a 2M-node DAG with a depth-3 payout window. Ask whether a person can have several referrers (forest versus real DAG) and whether "through" means bounty received or routed past the node to its ancestors. Brute force: BFS from every node, O(V × (V + E)). Better: Kahn's topological sort, O(V + E), then DP in topological order. Total payout by linearity of expectation: bounty × Σ_i p_i × (distinct ancestors of i within 3 hops), a 3-level reverse walk with a visited set (paths versus distinct nodes is the trap). Bounty received by v: bounty × Σ p_d over distinct descendants within 3 hops. Reachability is the hard one: subtree size in one post-order pass on a forest; on a DAG exact means transitive closure, O(V × E), or bitsets (2M × 2M bits is 500 GB), so estimate with a HyperLogLog sketch per node merged in reverse topological order, which never double-counts shared descendants. Constraint change (cycles): Kahn's algorithm leaving nodes behind is the detection; Tarjan's SCC, O(V + E), condenses each cycle to one node and reachability is answered on the condensation; for payout nobody is their own ancestor, which the visited set inside the window already enforces; bad edges are re-oriented by referral timestamp or reported as data-quality cases; without a depth bound the DP becomes a linear system, a Markov chain. Verify: brute force on a small random DAG, and check that Σ_v received equals the total payout. 10x: linear passes are fine at 20M; closure is not; shard by connected component (union-find).

**Drill 10, work orchestration.** Restate: a DAG scheduler with at-least-once workers, retries, lineage, backfills, and fair sharing across ten tenants. Brute force: one FIFO queue, rerun everything on any change, one tenant starves the rest. Better: readiness by Kahn's algorithm, an in-degree counter per task decremented as parents complete, ready at zero, O(V + E); a cycle is rejected at submission because Kahn's cannot drain it. Next task: per-tenant priority queues under weighted fair queueing, ordered within a tenant by critical-path length (longest path to a sink by DP), O(log T + log n) per decision; per-tenant token buckets for the judge quota. Failure: leases with heartbeats, an expired lease returns the task to the ready set; capped exponential backoff with jitter on retry, then a dead-letter set so a poison task cannot loop. Lineage and backfill: one idempotency key per task, hash(task type, input keys, code version, prompt version), which is both dedup key (run twice, write once) and lineage record; a new judge prompt changes the judge keys, so those outputs and everything downstream are recomputed while download and extract outputs are reused by key, cost O(affected subgraph). Constraint change (100k tasks from one tenant): fair queueing caps that tenant at its weight, so the other nine keep their share; add admission control (cap in-flight tasks per tenant, backpressure the submitter), size workers by Little's law. Verify: kill workers at random and count outputs per key (exactly one); measure per-tenant share under a flood; replay a prompt change and count keys reused. 10x: shard scheduler state by tenant; bookkeeping stays linear; the judge quota is the ceiling.
